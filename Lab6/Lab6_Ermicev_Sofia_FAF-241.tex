\section{Purpose of the Work}
The purpose of this laboratory work is to connect xv6 filesystem concepts with the source code and with observable behavior: file types, directory entries, inodes, hard links, block addressing, filesystem limits, and recursive traversal with a custom \texttt{find} program.

\section{Part 1. Reading What xv6 Shows}
\begin{lstlisting}
$ grep -n "T_DIR\|T_FILE\|T_DEVICE" kernel/stat.h
1:#define T_DIR    1 // Directory
2:#define T_FILE   2 // File
3:#define T_DEVICE 3 // Device
\end{lstlisting}
\figcap{Figure 1.1 -- Actual xv6 file-type constants}

\begin{lstlisting}
$ ls a
.              1 26 32
..             1 1 1024
\end{lstlisting}
\figcap{Figure 1.2 -- Actual listing of a newly created xv6 directory}

\begin{lstlisting}
struct dirent {
  ushort inum;
  char name[DIRSIZ] __attribute__((nonstring));
};
#define DIRSIZ 14
\end{lstlisting}
\figcap{Figure 1.3 -- Actual directory-entry definition inspected in kernel/fs.h}

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item Type 1 is \texttt{T\_DIR}, type 2 is \texttt{T\_FILE}, and type 3 is \texttt{T\_DEVICE}.
\item The root directory uses inode 1. Both \texttt{.} and \texttt{..} in the root point to inode 1 because root is its own filesystem parent.
\item An empty directory \texttt{a} has size 32 bytes because it contains two 16-byte directory entries, \texttt{.} and \texttt{..}.
\end{enumerate}

\section{Part 2. The mystat Program}
\begin{lstlisting}
$ mystat README . console
README: file, inode 2, links 1, size 2441 bytes
.: directory, inode 1, links 1, size 1024 bytes
console: device, inode 26, links 1, size 0 bytes
\end{lstlisting}
\figcap{Figure 2.1 -- Actual mystat output for a file, directory and device}

\begin{lstlisting}
$ ln README r2
$ mystat README r2
README: file, inode 2, links 2, size 2441 bytes
r2: file, inode 2, links 2, size 2441 bytes
$ rm README
$ mystat r2
r2: file, inode 2, links 1, size 2441 bytes
\end{lstlisting}
\figcap{Figure 2.2 -- Actual hard-link metadata observed with mystat}

The inode number assigned to a device can change after \texttt{fs.img} is rebuilt with a different set of user programs because \texttt{mkfs} recreates the image and assigns inodes again.

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item After \texttt{ln README r2}, both names referred to inode 2 and the link count became 2. Removing \texttt{README} left \texttt{r2} pointing to the same data while the count returned to 1.
\item \texttt{sys\_unlink} decrements \texttt{ip->nlink}; blocks are reclaimed only after the inode has no directory links and no remaining in-memory reference.
\item The on-disk xv6 inode contains type, major, minor, nlink, size and block addresses. This tree does not store Unix permission bits or a symbolic-link file type.
\end{enumerate}

\section{Part 3. Measuring File-System Limits}
\begin{lstlisting}
$ grep -n "define BSIZE\|define NDIRECT\|define NINDIRECT\|define DIRSIZ" kernel/fs.h
5:#define BSIZE   1024 // block size
26:#define NDIRECT   12
27:#define NINDIRECT (BSIZE / sizeof(uint))
54:#define DIRSIZ 14
\end{lstlisting}
\figcap{Figure 3.1 -- Actual xv6 filesystem constants}

\begin{lstlisting}
$ make clean
$ make fs.img 2>&1 | grep nmeta
nmeta 47 (boot, super, log blocks 31, inode blocks 13,
bitmap blocks 1) blocks 1953 total 2000
\end{lstlisting}
\figcap{Figure 3.2 -- Actual filesystem layout reported by mkfs}

\begin{lstlisting}
$ mkdir averyveryverylongname
$ ls
averyveryveryl 1 28 32
\end{lstlisting}
\figcap{Figure 3.3 -- Actual truncation of an xv6 filename to DIRSIZ characters}

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item The requested long name appears as \texttt{averyveryveryl} because \texttt{DIRSIZ} is 14.
\item With 12 direct blocks and 256 indirect entries, the maximum file size is \((12+256)\times1024=274432\) bytes, or 268 KiB.
\item The image contained 2000 blocks: 47 metadata blocks and 1953 data blocks in the observed build.
\end{enumerate}

\section{Part 4. The Recursive find Program}
\begin{lstlisting}
$ mkdir a
$ mkdir a/b
$ echo x > a/b/r2
$ echo y > a/r2
$ ln cat r2
$ find . r2
./a/b/r2
./a/r2
./r2
\end{lstlisting}
\figcap{Figure 4.1 -- Actual recursive find test for r2}

\begin{lstlisting}
$ find a b
a/b
\end{lstlisting}
\figcap{Figure 4.2 -- Actual recursive find test for directory b}

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item The output confirms that \texttt{find} traverses nested directories recursively and prints every matching path.
\item The program skips \texttt{.} and \texttt{..}, preventing an infinite recursion cycle, and ignores directory entries whose inode number is zero.
\item Each directory descriptor is closed after use, which is important because xv6 provides only a small number of open file descriptors per process.
\end{enumerate}

\section{Conclusion}
The work connected xv6's small filesystem API with its data structures and on-disk limits. Hard-link experiments demonstrated inode sharing, the constants in \texttt{fs.h} explained the name and file-size limits, and the custom \texttt{find} program used directory entries and recursive traversal to search the filesystem.
