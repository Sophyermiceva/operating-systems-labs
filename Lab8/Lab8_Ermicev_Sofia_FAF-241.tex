\section{Purpose of the Work}
The purpose of this laboratory work is to repeat the Linux process-control model inside xv6 and implement bidirectional parent-child communication using pipes. The work focuses on \texttt{fork()}, \texttt{exec()}, \texttt{wait()}, \texttt{pipe()}, \texttt{read()}, \texttt{write()}, and correct closing of unused descriptors.

\section{Environment and Preparation}
The new programs were added to xv6's \texttt{UPROGS} list:
\begin{lstlisting}
$U/_run\
$U/_pingpong\
\end{lstlisting}
\figcap{Figure 1.1 -- Actual UPROGS entries used for Lab 8}

\section{Part 1. run inside xv6}
\begin{lstlisting}
$ run
parent: my pid is 3
child: my pid is 4
hello from the child
parent: child 4 ended with status 0
\end{lstlisting}
\figcap{Figure 2.1 -- Actual run output when the child execs echo}

The program was then changed temporarily to execute \texttt{ls}. The child printed the xv6 root directory and the parent reported successful termination:
\begin{lstlisting}
parent: my pid is 3
child: my pid is 4
parent: child 4 ended with status 0
\end{lstlisting}
\figcap{Figure 2.2 -- Actual beginning/end of the successful ls exec experiment}

Finally, an invalid program name was tested:
\begin{lstlisting}
$ run
parent: my pid is 3
child: my pid is 4
exec failed
parent: child 4 ended with status 1
\end{lstlisting}
\figcap{Figure 2.3 -- Actual failed exec experiment in xv6}

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item xv6 uses \texttt{fork()}, \texttt{exec()} and \texttt{wait()}; Linux Lab 7 used \texttt{fork()}, \texttt{execlp()} and \texttt{waitpid()}. The overall process model is the same.
\item The line \texttt{hello from the child} is printed by the \texttt{echo} program after successful \texttt{exec()}, not by the old \texttt{run} code.
\item The xv6 failure status is 1 because the failure path calls \texttt{exit(1)}. Lab 7 used \texttt{exit(127)}, so Linux reported 127 there.
\end{enumerate}

\section{Part 2. pingpong}
\begin{lstlisting}
$ pingpong
4: received ping
3: received pong
\end{lstlisting}
\figcap{Figure 3.1 -- Actual pingpong output in xv6}

\subsection{Observe answers}
\begin{enumerate}[label=\arabic*.]
\item Two pipes are used because one carries data from parent to child and the other carries the reply from child to parent.
\item The parent waits for the reply in \texttt{read(c2p[0], \&b, 1)}. The blocking \texttt{read()} cannot complete until the child writes one byte to \texttt{c2p[1]}.
\end{enumerate}

\section{Comparison with Lab 7}
The same concepts appear in both laboratories. Lab 7 used Linux's richer interfaces such as \texttt{execlp()} and \texttt{waitpid()}, while Lab 8 used xv6's simpler \texttt{exec()} and \texttt{wait()}. Lab 7 built a one-direction pipeline between \texttt{ls} and \texttt{wc}; Lab 8 used two pipes so the parent and child could exchange data in both directions.

\section{Conclusion}
The experiments demonstrated that the fundamental process model is the same in xv6 and Linux: fork creates a child, exec replaces the current program, and wait collects child termination. The ping-pong exercise added explicit inter-process communication and showed how blocking reads naturally synchronize two processes.
